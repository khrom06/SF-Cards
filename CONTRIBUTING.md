# Contributing

Thanks for your interest! Issues and pull requests are welcome.

- **Before anything else:** never put personal data (names, addresses, IPs, tokens, real entity ids you would not share) in code, tests, screenshots or issues. Use fake data (`sensor.solar`, "Living room", "Car A").
- **Sources and build:** the library is written as modules in `src/` (one file per card, plus core, i18n, editors; numbered so that file-name order is load order) and built by `node scripts/build.mjs` into the single file HACS ships, `dist/sf-cards.js`: the modules are concatenated in file-name order, then minified with esbuild (a development tool only: the shipped file has no dependency and the tests read the readable `src/`). **Edit `src/`, never `dist/`**, then run the build and commit `src/`, `dist/` and `docs/sf-cards.js` together; `./test/run.sh` fails if `dist/` is out of date.
- **Translations:** every UI text has a neutral id like `health.all_good`, listed with its translations in `src/03-i18n-data.js` (order: fr, en, es, de, nl, it, pt, pl, ru, zh, ar; English is the fallback). Call `this.t("health.all_good")`. The French text still works as a legacy key. Tests fail on an unknown id or an incomplete entry.
- **Tests:** `./test/run.sh` (needs `node` and Chrome/Chromium). All tests must pass. Besides the snapshots, lint and layout, seven pages run in headless Chrome: `render.html` (every card, languages, editors), `security.html` (hostile states and configuration, confirmation), `editors.html` (every visual editor with hostile values everywhere), `lifecycle.html` (timers and subscriptions after a card is removed), `requests.html` (no repeated Home Assistant requests), `robustness.html` (missing, odd or failing data) and `a11y.html` (names, keyboard, RTL). `node scripts/taint.mjs` (≈1 min, also run by `run.sh`) instruments every `${…}` of every template (home-made parser, heuristic classification of the HTML context) and checks that no hostile value reaches the HTML unescaped in the scenarios it plays; an interpolation no scenario reaches must be on the reviewed list (`test/taint-reviewed.json`). It is a regression barrier, not a formal proof of the absence of XSS. Run it after touching markup, and read the sites it lists with `--list-unreached`. A test that guards a fix must fail without the fix. `node scripts/bench.mjs --throttle 4` measures render cost, requests and memory (compare two runs made on the same machine). It also checks **render snapshots** (`test/snapshots.json`: a hash of the rendered HTML of every card in every language, dark and light, with a frozen clock): a change that must not alter what is displayed has to leave every hash identical; if a visual change is intended, review it, then run `node test/snapshots.mjs --update` and commit the new file.
- **Languages:** every user-visible text goes through the translation table (11 languages). A missing translation falls back to English.
- **Screenshots:** 480×480 for the wall-panel card, fake data only; see the demo page (`docs/index.html`) for a ready-made mock Home Assistant.
- **Demo page:** `node scripts/build.mjs` also refreshes `docs/sf-cards.js`.

## The card contract (what "finished" means)

A card is not finished until it has what every other card has; `test/lint.js` (rule 9) fails otherwise: a full fixture in `test/fixtures.js` (`FULL`: this alone puts it in every generic test — render, security, editors, lifecycle, requests, robustness, accessibility, taint), an editor specification, a required-configuration rule (or a documented reason why it needs none), and a place in the README and the live demo. Behaviour the generic tests check for every card: no exception and a visible message on missing / unavailable / odd data, escaped text, no timer or subscription left after removal, no repeated request on a re-applied configuration, a name and keyboard access for every clickable element, light and dark theme, 11 languages, right-to-left. Data that is not measured must say so (see below).

**Measured, calculated, estimated.** A value read from a sensor is shown as is. A value computed from sensors by a rule that is always true (a sum, a difference) is shown as is. A value that rests on an assumption (for instance how a battery charge splits between solar and grid when the split is not measured) must be marked with `≈` and an explanatory tooltip, and the README must say what the assumption is.

## Adding a card

A new card touches these places (grep the name of a recent one, e.g. `sf-report-card`, to see each):
1. `src/29x-yourcard.js` — `class SfYourCard extends SfBase` with `render()` and `css()`; build all markup with `this.esc()`, call services only through `this.call()`, read entities through `this.st()` / `this.num()` / `this.ok()`. Any timer or subscription must be cleared in `disconnectedCallback`; a subscription must also be dropped if the card left the page while it was being set up (see `29h-weather.js`).
2. `src/30-registry.js` — add it to `SF_DEFS` (tag, class, picker name, description); `src/00-header.js` — list it in the header.
3. `src/04-config-rules.js` — `SF_REQ` (what must be configured, otherwise the "card to complete" frame appears).
4. `src/41-editor-specs.js` — the visual editor fields.
5. `src/03-i18n-data.js` — every text as an id with its 11 translations.
6. `test/fixtures.js` — a full configuration in `FULL`; `test/render.html` — card-specific checks if it has behaviour; then `node test/snapshots.mjs --update` after reviewing the changes.
7. `README.md`, `CHANGELOG.md`, `docs/index.html` (demo), and `node scripts/build.mjs`; run `./test/run.sh`.
